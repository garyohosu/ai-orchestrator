# AIエージェント・オーケストレーター要求仕様

## 1.1 起動単位の終端通知監視

CLI実行中もmailの公開`find_mails()`で同一送信者・受信者・Job-ID・Decision-IDの通知を非破壊検索する。`WAITING_FOR_DECISION`、`WAITING_FOR_WORKER`、`COMPLETED`、`FAILED`、`HUMAN_REQUIRED`、`REJECTED`、`CANCELLED`を検知した場合は、メールIDと状態を記録して短い猶予を与え、自然終了を待つ。自然終了しない場合は既存のWindows安全停止処理を使う。WAITING検知による停止はTIMEOUTに分類せず、Job全体の完了とは分離する。CLI内部タイムアウト、orchestrator監視期限、外側テストハーネス期限の順序を崩してはならない。

各CLIプロセスにはJob-ID・Decision-IDとは別のInvocation-IDを発行する。同一プロセスのACK、WAITING_FOR_DECISION、WAITING_FOR_WORKER、COMPLETED、FAILEDは同じInvocation-IDでなければならず、再開起動では新しいInvocation-IDを使用する。NO_REPLYは今回の実行でCLIを起動し、PID・プロセス開始時刻・起動前最大メールIDを記録し、同一Job/Decision/Invocationの有効な応答がなく、CLIが終了またはタイムアウトし、起動単位終端通知がない場合だけ送信する。CLI未起動、ACKのみ、WAITING_FOR_DECISION、WAITING_FOR_WORKER、COMPLETEDではNO_REPLYを送信しない。

## 1. 概要

本システムは、Windows 11上でPython、PowerShell、SQLiteを用いたメールシステムを使用し、Codex CLI、Claude CodeなどのAIエージェントを必要なときだけ起動する仕組みである。

人間またはChatGPTが最初の目的を与えた後、指揮AIと作業AIがメールを介して、作業依頼、成果物、QandA.md、回答、修正指示を受け渡す。

AIを常時起動せず、対象AI宛ての未読メールがある場合だけCLIを起動し、トークン消費とPC負荷を抑える。

## 2. 目的

次のやり取りを自動化する。

```text
人間またはChatGPTが目的を指示
  ↓
指揮AIが作業AIへメールで指示
  ↓
Pythonが未読メールを検出
  ↓
対象のAI CLIを起動
  ↓
作業AIが成果物とQandA.mdを作成
  ↓
作業AIが指揮AIへメールで報告
  ↓
Pythonが指揮AIを起動
  ↓
指揮AIが成果物とQandA.mdを確認
  ↓
回答または修正指示をメール
  ↓
完了まで繰り返す
```

## 5. フォルダ単位での再利用

`orchestrator`フォルダは、別のプロジェクトへフォルダ単位でコピーして利用できるものとする。

コピー先には、既存の`mail`フォルダが同じ階層に配置されていることを前提とする。

```text
別プロジェクト/
├── mail/
└── orchestrator/
```

`orchestrator`は、コピー元プロジェクト固有のPythonモジュール、絶対パス、環境変数、設定ファイルに依存してはならない。

コピー後にソースコードの書き換えを必要としないことを目標とする。

プロジェクトごとの差異は、`orchestrator/config.json`で指定できるものとする。

`config.json`は`orchestrator.py`自身の場所を基準に解決する。`project_path`を省略した場合の対象プロジェクトは、`orchestrator.py`の親ディレクトリの親（`project-root`）とする。指定する場合はプロジェクトルートを基準とした相対パスを使用し、正規化後にプロジェクトルート外となる指定は拒否する。絶対パスも設定できるが、コピー可能性を損なうため非推奨とする。

## 6. パスの基準

すべてのパスは、`orchestrator.py`自身の場所を基準に解決する。

カレントディレクトリを基準にしてはならない。

概念上、次の位置関係を使用する。

```text
orchestratorディレクトリ:
project-root/orchestrator/

プロジェクトルート:
project-root/

メールシステム:
project-root/mail/

対象プロジェクト:
project-root/
```

`project_path`で指定した対象パスが存在しない、またはディレクトリでない場合はAIを起動せず、元メールの送信者へ`DELIVERY_FAILED`通知を送る。

PowerShellをどのフォルダから起動しても、同じプロジェクトとメールDBを使用できるものとする。

Windowsのパス操作には、文字列連結ではなく`pathlib.Path`を使用する。

## 7. 既存メールシステムとの関係

メール機能は、同階層の`mail`パッケージを使用する。

```python
from mail import (
    register_user,
    list_users,
    send_mail,
    check_mail,
    receive_mail,
    find_mails,
)
```

メール取得の正式な仕様は次のとおりとする。

```python
check_mail(uid) -> int
receive_mail(uid) -> list[dict]
find_mails(*, sender_uid=None, recipient_uid=None, request_id=None,
           after_mail_id=None, sent_after=None, is_read=None,
           limit=None) -> list[dict]
```

`check_mail`は指定UIDの未読メール数を返すだけで、既読状態を変更しない。`receive_mail`は指定UIDの未読メールをメールID昇順で返し、取得したメールを同一トランザクション内で既読にする。受信と既読化は分離しない。

`find_mails`は既読状態を一切変更しない読み取り専用の検索APIである。オーケストレーターは、返信メールの確認（30章）とSTALE復旧時の元メール状態確認（24章）に`find_mails`を使用する。これらは他AI宛てのメールを既読化せずに参照する必要があり、`check_mail`は未読数しか返さず、`receive_mail`は取得と同時に既読化して本来の受信者からメールを奪ってしまうため、いずれも使用できない。

オーケストレーターがメールDBへSQLで直接アクセスしてはならない。SQLiteのテーブル名、列名、接続方法をオーケストレーター側が知る構造にせず、必ず`mail`パッケージの公開関数を経由する。`request_id`による絞り込みは`mail`側が件名の部分文字列一致として解決するため、オーケストレーターは件名の格納形式に依存しない。

`find_mails`の追加は検索機能の追加であって、AI起動処理やオーケストレーション処理の追加ではない。`mail`パッケージは引き続きAI CLIを検出・起動せず、`orchestrator`を削除しても`mail`単体で動作する。

初期版ではメールテーブルへ「取得中」「処理済み」「処理失敗」の状態を追加しない。また、既読メールを自動的に未読へ戻さない。AIが受信後に異常終了した場合は、元メールの送信者へエラー通知を送り、再実行は同じ依頼IDを付けた新しいメールで行う。対象AIがまだメールを受信していないことが明らかなCLI起動失敗などに限り、設定回数まで起動を再試行できる。

メールシステム本体へ、AI起動処理やオーケストレーション処理を追加してはならない。

役割を次のように分離する。

```text
mail:
ユーザー登録、メール送信、未読確認、メール受信

orchestrator:
未読監視、AI起動、終了監視、再試行、引継ぎ、ログ
```

`orchestrator`を削除しても、`mail`単体のメール送受信機能は使用できるものとする。

## 8. 基本方針

* できるだけ単純な構成とする
* Python標準ライブラリだけを使用する
* PowerShellから簡単に起動できる
* AIを待機目的で常駐させない
* 未読メールがあるAIだけを起動する
* 一度の起動で複数の未読メールを処理する
* 成果物はファイルとして保存する
* メールには成果物の相対パスと要約を記載する
* 長い成果物全文をメールに貼り付けない
* 既存スキル内部の工程は管理しない
* PythonはAIの代わりに設計判断を行わない
* 初期版ではAIを1人ずつ直列に起動する
* AIの処理順は`config.json`のエージェント定義順とする

## 9. 役割

### 9.1 人間またはChatGPT

* 最初の目的、制約、初期指示を指定する
* 指揮AIを1回だけ手動で起動する
* AIだけで判断できない事項へ回答する
* 最終成果物を確認する
* 必要に応じて処理を停止する

人間またはChatGPTは、メールシステム上の作業依頼送信者ではない。指揮AIへ初期目的を与える起動者として扱う。最初の作業依頼メールを実際に`send_mail`で送信するのは指揮AIであり、その送信者UIDは指揮AIのUIDとなる。

### 9.2 Pythonオーケストレーター

* SQLiteメールを定期的に確認する
* 未読メールがあるAIを特定する
* 宛先に対応するCLIを起動する
* AIの二重起動を防止する
* CLIの終了、失敗、タイムアウトを記録する
* 未読メールがなければ待機する
* AIによる判断や成果物作成は行わない

### 9.3 指揮AI

初期版ではCodex CLIを想定する。

* 人間またはChatGPTから初期目的・制約・初期指示を受け取る
* 依頼内容を確定する
* 依頼IDを生成する
* `send_mail`を使用して作業AIへ最初の作業依頼メールを送信する
* 作業AIへメールで指示する
* 成果物とQandA.mdを確認する
* 自動回答可能な質問へ回答する
* 修正または再レビューを指示する
* 完了条件を確認する
* 人間判断が必要な場合は処理を停止する

### 9.4 作業AI

初期版ではClaude Codeを想定する。

* 自分宛ての未読メールを読む
* 指定された作業を実行する
* 必要に応じて既存スキルを使用する
* 成果物を指定場所に保存する
* 不明点を`QandA.md`に記録する
* 実行結果を指揮AIへメールで報告する
* 処理対象がなくなったら終了する

## 10. 設定

プロジェクトごとの設定は次に保存する。

```text
orchestrator/config.json
```

最低限、次を設定できるものとする。

```text
メール確認間隔
CLI実行タイムアウト
返信確認タイムアウト
最大往復回数
最大再試行回数
最大連続実行時間
AI名とUID
AI名と起動コマンドの対応
対象プロジェクト
ログ保存先
引継ぎ保存先
CLI出力のストリーム別保存上限
エラー通知へ掲載する出力末尾の上限
依頼ID単位の最大自動引継ぎ回数
AIごとの代替AI一覧
```

既定値は次のとおりとする。時間の単位は秒とする。

```text
メール確認間隔: 5
CLI実行タイムアウト: 1800
返信確認タイムアウト: 30
最大往復回数: 10
最大再試行回数: 2
最大連続実行時間: 14400
CLI出力のストリーム別保存上限: 1048576バイト
エラー通知へ掲載する出力末尾の上限: 8192バイト
依頼ID単位の最大自動引継ぎ回数: 3回
```

`最大再試行回数`は追加試行回数であり、既定値2回は初回と合わせて最大3回の起動試行を意味する。`最大往復回数`と再試行回数は別々に数える。完了報告、エラー通知、単なる受領通知は往復回数に含めない。常時監視モードの`最大連続実行時間`は0の場合だけ無期限とする。

設定を省略した場合に使用する安全な既定値を用意する。

APIキー、パスワード、認証トークンを`config.json`に保存してはならない。

各CLIの認証は、事前に利用者が完了させておく。

## 11. CLIの検出

初期版では次に対応する。

```text
Codex CLI
Claude Code
```

CLIの場所は、次の順で確認する。

1. `config.json`へ明示されたコマンド
2. WindowsのPATH
3. CLIごとの既定コマンド名

例：

```text
codex
claude
```

CLIが見つからない場合は、推測した場所から実行せず、エラーとして記録する。

PowerShellの`Get-Command`と同等の確認結果になることを目標とする。

将来的に次を追加できるものとする。

```text
Antigravity CLI
Grok
Gemini CLI
その他の非対話実行可能なCLI
```

## 12. AIの起動

Pythonから`subprocess`を使用してAI CLIを起動する。

シェルへ文字列を渡して実行する方式を避け、コマンドと引数を分離して起動する。

AIの起動時には、原則として短い固定指示を渡す。

```text
あなたは{agent_name}です。
UIDは{uid}です。

プロジェクト内のmailパッケージを使い、自分宛ての未読メールを確認してください。
引継ぎ情報がある場合は確認してください。
メールの指示を実行し、指定された宛先へ結果をメールしてください。
処理対象がなくなったら終了してください。
```

具体的な作業内容はSQLiteメールから取得する。

## 13. PowerShellからの起動

最低限、次の方法で起動できるものとする。

プロジェクトルートから実行：

```powershell
python .\orchestrator\orchestrator.py
```

`orchestrator`フォルダから実行：

```powershell
python .\orchestrator.py
```

Python Launcherを使用する場合：

```powershell
py -3 .\orchestrator\orchestrator.py
```

実行場所が異なっても、同じ`mail`フォルダと対象プロジェクトを検出する。

PowerShell用の補助スクリプトを用意する場合も、必須の処理はPython側に実装する。PowerShellスクリプトだけに重要な処理を持たせない。

## 14. 実行モード

最低限、次の2モードを用意する。

### 常時監視モード

```powershell
python .\orchestrator\orchestrator.py
```

未読メールを定期確認し、設定または明示的な停止操作により停止するまで待機する。最大連続実行時間の既定値は4時間であり、超過時は安全停止する。

### 一巡モード

```powershell
python .\orchestrator\orchestrator.py --once
```

全AIの未読メールを一度確認し、必要なAIを起動して処理結果を確認した後に終了する。起動したAIが返信を作成する前に終了してはならない。起動直前の競合などにより未読メールが0になった場合は、返信を要求せず`NO_WORK`をログに記録して正常終了する。

## 15. 未読メール監視

Pythonオーケストレーターは、設定された間隔で未読メールを確認する。未読数の確認には`check_mail(uid)`を使用し、実際に処理するメールの取得には`receive_mail(uid)`を使用する。

未読メールがなければ、次の確認まで待機する。

待機中にAIやLLMを呼び出してはならない。

同じAIが実行中の場合は、新しいプロセスを起動しない。

AI終了後は必ず未読数を再確認する。未読メールが残っている場合は、必要に応じて再度起動する。AI起動中に届いた新着メールを同じプロセスが処理しても、終了後に再起動してもよいが、一度の起動にはCLI実行タイムアウトを適用する。

## 16. 同時実行

初期版では、AIを1人ずつ順番に起動する。

同時に複数AIを実行する機能は必須としない。

複数のAIに未読メールがある場合は、`config.json`に記載されたエージェント定義順に処理する。登録UID順は使用しない。同じAIに複数の未読メールがある場合は、メールID昇順で処理する。

## 17. 依頼ID

各作業には一意の依頼IDを付ける。依頼IDは、作業依頼メールを最初に作成する側が生成する。最初の作業依頼については、指揮AIが依頼内容を確定したうえで依頼IDを生成する（9.1, 9.3）。

例：

```text
JOB-20260730T063015Z-A3F91C2D
```

依頼IDはメール件名に含める。

```text
[JOB-20260730T063015Z-A3F91C2D] SPEC.mdから詳細設計を作成
```

自動生成形式は`JOB-{UTC日時}-{ランダム8桁}`とし、ランダム部分はUUIDから生成する。連番形式は表示例として採用しない。新しい目的または新しい作業、元の作業とは独立したやり直しでは新しい依頼IDを使用する。同じ依頼への返信・質問・回答・修正指示、QandA回答後の再開、失敗後の再送では同じ依頼IDを使用する。オーケストレーターは同じ依頼IDを持つメールを同一作業の履歴として扱う。

初期版では専用ジョブ管理DBを必須とせず、メール履歴と引継ぎ情報から追跡できればよい。

## 18. 成果物

* 成果物は対象プロジェクト内に保存する
* メールには成果物の相対パスを記載する
* 絶対パスをメールに記載しない
* 指揮AIは必要な成果物だけを読む
* AIが指定範囲外のファイルを変更しないよう指示する
* 成果物に日本語を含められるものとする

## 19. QandA.md

作業中の不明点は、対象プロジェクトの`QandA.md`に記録する。ファイルが存在しない場合は、作業AIが新規作成する。

各質問には最低限、次を含める。

```text
質問番号
状態
重要度
質問者
対象ファイル
質問内容
推奨案
回答
```

状態は次を使用する。

```text
OPEN
ANSWERED
APPLIED
```

指揮AIは原則として`OPEN`の質問だけを確認する。質問番号の形式、採番方法、重複判定、同時更新時の扱いはQandA.mdの運用規約で定める。

要求変更、破壊的操作、外部公開、課金、契約、セキュリティなどの重要判断は人間へ戻す。

## 20. 引継ぎ

各依頼について、再起動後も処理を継続できる引継ぎ情報を保存する。

保存場所：

```text
orchestrator/checkpoints/
```

引継ぎには最低限、次を含める。

```text
依頼ID
目的
現在の状態
決定事項
成果物
未解決事項
次に行うこと
最終更新日時
```

引継ぎは長い会話履歴の代わりとして使用する。

次回起動時は次を優先して読む。

1. 引継ぎ情報
2. 未回答のQandA
3. 必要な成果物
4. 対象メール

## 21. 文字コード

システム全体でUTF-8を使用する。

次をUTF-8として扱う。

* メール件名
* メール本文
* CLIへの入力
* CLIの標準出力
* CLIの標準エラー
* ログ
* 設定ファイル
* 引継ぎファイル
* 成果物

Windowsの既定コードページに依存しない。

PythonからCLIを起動する際は、Unicode文字列を安全に渡せる方法を使用する。

必要に応じて子プロセスへ次の環境を設定する。

```text
PYTHONUTF8=1
PYTHONIOENCODING=utf-8
```

日本語を含むメールを送受信し、文字化けしないことを必須とする。

## 22. トークン節約

次の方法でトークン消費を抑える。

* 未読メールがないAIは起動しない
* 待機処理をPythonだけで行う
* メールへ成果物全文を貼らない
* 必要なファイルだけをAIに読ませる
* 引継ぎ情報を使用する
* 解決済みのQandAを毎回読み直さない
* 一度の起動で未読メールをまとめて処理する
* 作業AIの内部工程を指揮AIへ逐次報告しない
* 完了、質問、失敗など判断が必要な時点だけ指揮AIへ報告する

## 23. ログ

ログは次へ保存する。

```text
orchestrator/logs/
```

最低限、次を記録する。

```text
日時
依頼ID
メールID
起動したAI
実行コマンドの秘密情報を除いた部分
開始時刻
終了時刻
終了コード
実行結果
作成・変更ファイル
エラー
次の宛先
```

APIキー、認証情報、Cookie、秘密の環境変数を記録しない。

## 24. 実行時情報

一時的な実行情報は次へ保存する。

```text
orchestrator/runtime/
```

次の用途に使用できる。

```text
二重起動防止
実行中AIの記録
プロセスID
一時ログ
停止要求
再試行回数
CLI stdout/stderrの読み取り中間状態
RATE_LIMITED判定と引継ぎ状態
```

実行中AIの情報には最低限、次を保存する。

```text
PID
プロセス開始時刻
AI名
AIのUID
依頼ID
元メールID
起動コマンド
オーケストレーターが記録した起動日時
```

プロセスの存在確認ではPIDだけを使用せず、Windowsから取得したプロセス開始時刻と保存した開始時刻を照合する。PIDが同じでも開始時刻が一致しない場合は別プロセスとして扱い、PIDだけを根拠に別プロセスを終了してはならない。プロセス開始時刻を確認できない場合は安全のため実行中とはみなさず、`STALE`候補として扱う。

実行時情報が残っていても、実際のプロセスが存在しない場合は復旧できるものとする。

オーケストレーター起動時に対応するプロセスが存在しない実行情報を`STALE`としてログへ記録する。元メールが未読なら再処理候補とし、既読で返信がない場合は元の送信者へ異常終了通知を送り、返信済みなら完了済みとして整理する。

元メールの既読状態と返信の有無は`find_mails`で確認する。`receive_mail`を使用してはならない。使用すると、対象AIがまだ受信していない元メールを奪って既読化し、再処理候補としての判定自体を破壊するためである。

STALE復旧における返信の判定条件は、30章「返信メールの確認」と同一とする。依頼IDの一致だけで返信済みと判定してはならない。`sender_uid`に実行情報へ記録された処理対象AIのUID、`recipient_uid`に期待する返信先UID、`request_id`に依頼ID、`after_mail_id`に元メールID、`sent_after`に実行情報へ記録された起動日時を指定する。これにより、同じ依頼IDを持つ古い返信や、別の送受信者間のメールを完了済みと誤判定しない。オーケストレーター自身が強制終了した場合も、次回起動時に同じ復旧処理を行う。

## 25. 停止条件

次の場合は自動処理を停止する。

* 人間による判断が必要
* 最大往復回数へ到達
* 同じ修正が繰り返されている
* CLIの認証が切れている
* CLIが繰り返し異常終了する
* タイムアウトが繰り返される
* 対象ファイルが見つからない
* 破壊的操作が必要
* 外部公開や外部送信が必要
* 課金や契約変更が必要
* セキュリティ上の問題を検出した

停止理由と現在状態をログおよび引継ぎに記録する。

常時監視モードは、Ctrl+Cまたは`orchestrator/runtime/stop.request`で停止できる。停止要求を検出した場合は新しいAIを起動せず、実行中AIの終了を原則として待つ。CLI実行タイムアウトまでに終了しない場合はプロセスを終了し、中断した処理をログと引継ぎへ記録し、必要に応じて元メールの送信者へ通知してからオーケストレーターを終了する。処理済みの`stop.request`は削除する。AI実行中に再度Ctrl+Cを受けた場合は強制停止を許可するが、その事実をログ・引継ぎへ記録し、元メールの送信者へ通知する。

## 26. 障害時の動作

CLI起動失敗時は、対象AIがまだメールを受信していないことが明らかな場合に限り、最大再試行回数まで再試行する。AIがメールを受信して既読にした後の作業失敗は、自動再試行の対象としない。

CLIのstdoutとstderrは無制限にメモリへ保持せず、ストリームごとに`orchestrator/logs/`配下へマスキングしながら上限付き保存を行う。上限到達後も読み取りを継続してパイプ詰まりを防止する。通知へはマスキング後の末尾だけを掲載する。

再試行上限へ達した場合は、状態を次のいずれかとして記録する。

```text
FAILED
RATE_LIMITED
HUMAN_REQUIRED
```

PowerShell、PC、オーケストレーターを再起動しても、SQLiteメール、引継ぎ情報、成果物から未完了作業を確認できるものとする。

CLIの判定は終了コードだけで行わず、起動可否、タイムアウト、返信メールの有無・依頼ID・送受信者UID、AIが返信した状態、およびCLIアダプターがstdout/stderrから抽出した有限長の判定根拠を組み合わせる。CLIを起動できない、CLIが見つからない、または対象プロジェクトが存在しない場合は`DELIVERY_FAILED`、アダプターが利用制限を示す根拠を検出した場合は`RATE_LIMITED`、0以外の終了コードまたは予期せぬ終了は`FAILED`、タイムアウトは`TIMEOUT`、NO_REPLYの条件を満たした場合だけ`NO_REPLY`とする。未読メールが0でAIを起動しなかった場合は`NO_WORK`をログに記録し、NO_REPLYを送信しない。認証切れ、対象ファイル不足、破壊的操作、人間判断の必要性は、可能な場合はAIからの返信状態を優先し、判定できない場合は`HUMAN_REQUIRED`として停止する。標準出力や標準エラーの単独判定を共通分類器が行ってはならず、CLI固有判定はアダプターが根拠付きで返す。

`RATE_LIMITED`は通常のCLI起動失敗再試行を行わず、設定された代替AIへ同じ依頼IDで引き継ぐ。代替AIの選択順、担当履歴、引継ぎ回数、循環防止、候補全滅時の`HUMAN_REQUIRED`遷移は`orchestrator/FAILOVER_DESIGN.md`で定義する。

## 29. 初期動作確認

最初の動作確認では、次の処理を実行する。

```text
1. 指揮AIとClaude Codeをメールシステムへ登録
2. 人間またはChatGPTが指揮AIを1回だけ手動起動し、
   指揮AIがClaude Codeへ日本語の作業依頼を送信
3. オーケストレーターが未読を検出
4. Claude Codeを起動
5. Claude Codeが既存スキルを実行
6. 成果物とQandA.mdを作成
7. Claude Codeが指揮AIへ完了メールを送信
8. オーケストレーターが指揮AI宛てメールを検出
9. Codex CLIを起動
10. Codex CLIが成果物とQandA.mdを確認
11. Codex CLIが回答または修正指示をメール送信
12. オーケストレーターがClaude Codeを再起動
13. Claude Codeが回答を反映
14. 完了メールを送信
15. 未読メールがなくなり、全AIが終了
```

手順2の指揮AI起動だけは、人間またはChatGPTによる手動操作とする。オーケストレーターによる自動処理は、最初の作業依頼メールが送信された手順3以降を対象とする。したがって手順2で送信されるメールの送信者UIDは指揮AIのUIDであり、以降に作業AIで発生するエラー通知、回答、QandA、完了報告の返信先も原則として指揮AIのUIDとなる。

* 未読メールがない間はAIを起動しない

* 日本語のメール、ログ、CLI入出力が文字化けしない

### システム送信者

オーケストレーターは、エラー通知を送信するため、メールシステムへシステムユーザーとして登録する。

登録名は次とする。

`orchestrator`

通常のAIエージェントと同様に一意のUIDを取得する。

オーケストレーターは成果物を作成したり、AIの代わりに回答したりしない。CLIの起動または処理に失敗したことを通知する場合だけメールを送信する。

### CLI異常時の送信元通知

AI宛てのメールを処理するためにCLIを起動したものの、正常な応答を得られなかった場合、オーケストレーターは元メールの送信者へエラー通知メールを送信しなければならない。

ログへ記録するだけで処理を終了してはならない。

これにより、送信元AIが返信を永遠に待ち続けることを防止する。

### 通知対象

最低限、次の場合にエラー通知メールを送信する。

* 対応するCLIが見つからない
* AI名に対応する起動設定がない
* CLIプロセスを起動できない
* CLIの認証が切れている
* CLIが異常終了した
* CLIが0以外の終了コードを返した
* CLIがタイムアウトした
* CLIが強制終了された
* CLIが正常終了したが、指定時間内に返信メールを送信しなかった
* AIが受信メールを処理しなかった
* 最大再試行回数へ到達した
* 対象プロジェクトまたは必要ファイルが見つからない
* オーケストレーター内部で処理継続不能な例外が発生した

### 通知先

エラー通知の送信先は、処理対象となった元メールの送信者UIDとする。

元メール:

```text
送信者: UID000001
受信者: UID000002
```

UID000002のCLI起動または処理に失敗した場合、通知先はUID000001とする。

エラー通知:

```text
送信者: orchestratorのUID
受信者: UID000001
```

### 件名

エラー通知メールの件名は、元の依頼IDを維持し、配達または処理に失敗したことが分かる形式とする。

`[JOB-20260730T063015Z-A3F91C2D][DELIVERY_FAILED] claude_1の処理に失敗`

タイムアウトの場合：

`[JOB-20260730T063015Z-A3F91C2D][TIMEOUT] claude_1から応答なし`

返信メールが作成されなかった場合：

`[JOB-20260730T063015Z-A3F91C2D][NO_REPLY] claude_1が返信せず終了`

### 本文

エラー通知メールには最低限、次を含める。

* 状態
* 依頼ID
* 元メールID
* 元の送信者UID
* 処理対象AI名
* 処理対象UID
* 失敗段階
* 失敗理由
* CLI終了コード
* 実行時間
* 再試行回数
* 最終試行日時
* 元メールの状態
* 推奨する次の対応

例：

```text
状態: DELIVERY_FAILED
依頼ID: JOB-20260730T063015Z-A3F91C2D
元メールID: 12
元の送信者UID: UID000001
処理対象AI: claude_1
処理対象UID: UID000002
失敗段階: CLI実行
失敗理由: 制限時間内に処理が終了しませんでした
CLI終了コード: 取得不可
実行時間: 1800秒
再試行回数: 3
最終試行日時: 2026-07-30T06:30:00.000Z
元メールの状態: 処理失敗

推奨する次の対応:
Claude Codeの認証状態とプロセスを確認し、必要であれば同じ依頼IDで再送してください。
```

### エラー情報の制限

エラー通知メールへ次を含めてはならない。

* APIキー
* 認証トークン
* Cookie
* パスワード
* 秘密の環境変数
* メール本文全文
* CLIへ渡したプロンプト全文
* 個人情報を含む絶対パス
* 標準出力または標準エラーの無制限な全文

標準出力・標準エラーを記載する場合は、秘密情報を除去した末尾部分だけとし、各ストリームの設定上限を超えてはならない。

詳細ログがある場合は、本文へログの相対パスを記載する。

CLI出力を保存した場合は、stdout/stderrそれぞれの相対パス、保存済みマスキング後バイト列のSHA-256、保存量、切捨て有無をログへ記録する。

### 再試行と通知時期

一時的な失敗については、設定された回数まで再試行できる。

```text
1回目失敗
  ↓
再試行
  ↓
2回目失敗
  ↓
再試行
  ↓
最大回数到達
  ↓
送信元へエラー通知
  ↓
自動再試行を終了
```

最大再試行回数へ達するまでは、送信元へ途中経過を毎回通知する必要はない。

ただし、再試行とタイムアウトを含めた処理時間には有限の上限を設ける。

上限へ達した場合は、必ずエラー通知を送信する。

### 返信メールの確認

CLIの終了コードが0であっても、それだけでは正常完了と判定しない。

処理対象AIがInvocationの終端結果メールを作成したことを確認する。結果メールは元メールの送信者へ戻る場合と、委譲先の第三者AIへ送られる場合があるため、宛先UIDだけからInvocationの終了を推測しない。

最低限、次を照合する。

* 返信メールの送信者UIDが、処理対象AIのUIDと一致すること
* 返信メールIDが、処理対象となった元メールIDより大きいこと
* 返信メールがCLI起動後に作成されていること
* 本文がJSON objectであり、`job_id`、`decision_id`、`invocation_id`、`parent_invocation_id`、`root_invocation_id`、`trigger_mail_uid`が起動時の構造化メタデータと完全一致すること
* 本文の`invocation_result`が`COMPLETED`、`DELEGATED`、`WAITING`、`FAILED`のいずれかであり、`status`と矛盾しないこと

CLIが正常終了した後も、`返信確認タイムアウト`まで`find_mails`で確認する。同時間内に期待する返信メールが存在しない場合は、`NO_REPLY`として元の送信者へ通知する。同じ依頼IDを持つ古いメールは返信として扱わない。

返信確認には`find_mails`を使用し、`sender_uid`に処理対象AIのUID、`after_mail_id`に元メールID、`sent_after`にCLI起動時刻を指定する。取得後に上記の構造化メタデータを照合する。`recipient_uid`と件名の依頼IDは検索条件にせず、表示・配送上の補助情報として扱う。返信確認によって返信メールを既読化してはならない。返信先AIが自分で`receive_mail`を実行するまで、当該メールは未読のまま維持される。

複数の有効な結果がある場合は、メールIDが最小の結果を正本とし、後続を重複として診断記録する。タイムアウト直後は設定された有限のgrace期間だけ最終照会し、正しい結果があれば採用する。終端確定後の遅延結果で状態を再オープンしない。

これにより「CLIは終了したが、依頼元AIが待ち続ける」状態を防ぐ。

### タイムアウト時

CLIが設定時間内に終了しない場合は、次の処理を行う。

* タイムアウトをログへ記録する
* 対象CLIプロセスを終了する
* 必要に応じて設定回数まで再試行する
* 再試行上限へ達した場合は送信元へTIMEOUTメールを送る
* 引継ぎ情報へ未完了であることを記録する
* 対象依頼の自動処理を停止する

子プロセスから派生したプロセスがある場合は、取り残されたプロセスがないか確認する。

CLIがメールを受信して既読にした後のタイムアウトは自動再試行の対象とせず、`TIMEOUT`通知を送って対象依頼の自動処理を停止する。CLIを起動できなかった場合など、対象AIがまだメールを受信していないことが明らかな場合だけ、設定回数まで起動を再試行できる。

### 失敗確定後の扱い

エラー通知を送信した後、同じ元メールに対する自動起動を無制限に繰り返してはならない。

失敗が確定した元メールは、オーケストレーター側で終端状態として記録する。

* `FAILED`
* `TIMEOUT`
* `NO_REPLY`
* `RATE_LIMITED`
* `DELIVERY_FAILED`

再実行する場合は、次のいずれかを必要とする。

* 送信元AIが同じ依頼IDで再送する
* 人間が再試行を指示する
* 設定された明示的な再開操作を行う

### エラー通知による無限ループ防止

オーケストレーターが送信したエラー通知メールについて、返信を必須としない。

エラー通知は終端通知として扱う。

エラー通知の受信者が起動できなかった場合でも、別のエラー通知を同じ相手へ無限に作成してはならない。

元メールの送信者がorchestrator自身だった場合は、メールを再帰的に送信せず、ログと引継ぎ情報へ記録して人間判断状態にする。

エラー通知メール自体の送信に失敗した場合も、再帰的なエラー通知を作成しない。通知失敗をログと引継ぎ情報へ記録し、対象依頼を`HUMAN_REQUIRED`として自動処理を停止する。元メールの送信者UIDが存在しない、削除済み、または不正な場合も同じ扱いとし、通知先を別AIへ変更しない。オーケストレーター自身への通知も作成しない。

### 受け入れ条件への追加

次を初期版の受け入れ条件へ追加する。

* CLIが見つからない場合、元メールの送信者へエラー通知が届く
* CLI起動失敗時、元メールの送信者へエラー通知が届く
* CLI異常終了時、元メールの送信者へエラー通知が届く
* CLIタイムアウト時、元メールの送信者へエラー通知が届く
* CLIが正常終了しても返信メールがない場合、NO_REPLY通知が届く
